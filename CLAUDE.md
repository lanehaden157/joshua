# Joshua

How this repo behaves. The artifact contract lives in
`joshua_study_style_reference.md` and is authoritative over this file.

Built on **bible-core** (vendored in `biblecore/`, version in
`biblecore/CORE_VERSION`). The shared shape and the ways a book is expected to
differ are in `bible-core/ARCHITECTURE.md`; shared wording defaults in
`bible-core/canon/conventions.md`. The chat-side loop is `core-workflow.md`
(vendored, synced); `CHAT_SIDE_INSTRUCTIONS.md` is pasted by hand into the
project's instruction field and only carries what's Joshua-specific.
Optional components (echo, story) come from core's registry via `book.json`
`components`; `css/core.css`, `css/components.css`, `data/components.json` and
`components-reference.md` are generated by the build. The book's own look is
`css/theme.css`. `source-artifacts/` is current for every built unit: edit
there and re-port rather than editing `units/` by hand.

**State:** `python -m biblecore book` prints where the book stands (units
built and planned, tracked threads, core pin vs vendored copy, sync
status), read from its data. It isn't written here, so it can't go stale.

## Commands (run from this folder)

    python -m biblecore book             # where the book stands (see State above)
    python -m biblecore port 5 [--dry]   # port source-artifacts/joshua_05_translation.html (--force re-ports;
                                         # --answers FILE: {question topic: answer} so a dry run's answers carry over)
    python -m biblecore build            # everything downstream of units/*.html
    python -m biblecore audit            # tracked-thread coverage (--ids ROOT to preview an id set);
                                         # gaps end with ready `add` JSON for retrofit/retrofit-tags.json
    python -m biblecore test [--quick]   # check the book: pin, units, contracts, build idempotence
    python -m biblecore sync             # mirror chat-side files, commit and push (after Lane's OK)
    python tools/build_english.py        # Joshua-english.txt from the WEB USFM (Joshua-only)

`python -m biblecore` lists the rest: `colour` and `data-w` for promoting a
thread, `leads`, `units-from-map`, `corpus`, `migrate` after re-vendoring.

GitHub Actions runs `python -m biblecore test` on every push
(`.github/workflows/tests.yml`, shipped unchanged by bible-core's template;
commits touching only `project-side/` or session files skip it).

`book.json` holds everything book-specific (closed keys: an unknown key is an
error). Change behaviour for this book by adding a book-local module that
wraps a core function, not by editing `biblecore/`; `python ../bible-core/tools/core_diff.py`
reports edits made there. Update the vendored copy with
`python ../bible-core/tools/core_sync.py .` (a core release does this for
every book). `python ../bible-core/tools/core_diff.py . --template` shows the
template changes this book hasn't taken (optional; `--set-base` after
taking them).

**Concurrent sessions.** Another session may be editing `../bible-core` or this
repo at the same time. See "Concurrent sessions" in `../bible-core/CLAUDE.md`:
check `git status` first, work in a worktree if it's dirty, stage explicit
paths, and check `book.json`'s `core` version after vendoring.

## Site

The build's `assets` step writes the app shell (`index.html`, `app/*.js`) and
`css/core.css`, `components.css`, `division.css` from bible-core, with the
book name filled in and a content hash on every link. Each one says
"generated, don't edit", and `python -m biblecore test` reports a hand edit.
This book's look is `css/theme.css` plus the `book.json` settings (groupings,
components, theme). A change to the shell itself goes into bible-core's
`biblecore/web/` and reaches the book with the next vendor and build.

## Generated paths

Commit `data/`, `css/`, `app/`, `index.html`, `units/`, `canon-leads/` and
`threads-digest.md`: the build regenerates them and they are what the site and
the hub serve, so a changed one belongs in the commit that caused it. `out/`
is gitignored scratch (thread deltas, reports); never commit it. A tree that
is dirty only in `out/` is clean.

## Policy files

`data/threads.json` and `data/roots.json` are policy: the porter proposes, a
human applies. Who decides whether a candidate becomes a tracked thread is set
in the style reference §3. Thread colours come from `python -m biblecore colour`
by default (colours picked by eye collided before); hand-pick one only if Lane
asks. If `data/palette.json` runs short, expand it by
generation, not by eye.

Promoting a thread makes every occurrence in every built unit need `data-w`.
Usually `python -m biblecore data-w N` fills them in place; what it can't
decide, and the port's coverage gaps, go in `retrofit/retrofit-tags.json`.

**Retrofit recipe** (per promoted root, per unit, for the verses `data-w`
reports as undecided):

1. Compare the root's occurrences in `Joshua-words.tsv` for the verse with
   the fragment's `<span class="r" data-root="ROOT">` spans, in order.
2. Where the counts differ, look closer: one span over two source words (one
   `retag`, or split by hand); one source word as two English spans (keep the
   span a reader recognises as the word and `unwrap` the other: `rl` still
   picks up the root's colour, so demoting isn't enough); or a truly untagged
   occurrence (`add`).
3. Same root and same text twice in a verse: `retag`'s `occ` (1-based).
4. One entry per occurrence: `{"unit", "verse", "from", "to", "text", "w"}`.
5. Re-run `python -m biblecore build` (it replays the retrofit file and
   audits); every promoted root should report clean.

**Porting gotchas.** Re-porting a built unit needs `--force`, and it should be
deliberate: an earlier port re-ported unit 1 from a stale source artifact and
silently lost four local roots.

## Asking Lane

Questions for Lane (the porter's `questions[]`, wording calls, thread
decisions) go through the **AskUserQuestion popup** with multiple-choice
options, best provisional choice first and marked "(Recommended)", batched
four per call, rather than a list in chat.

## Corpus

Pins: **morphhb 2.0.2** (`package.json`; `npm ci` restores it), **HebrewLexicon
@ `21c9add`** (`corpus/lexicon/`), **WEB classic** USFM (`corpus/web/`).

Checked against printed BHS: **658 verses** (chapter 21 has 45; 21:36–37
present, unmarked), **10,083 words** (10,051 running text + 32 Qere rows), **52
petuḥah + 42 setumah = 94 breaks**. If a count drifts on re-fetch, flag it
loudly: it likely means the corpus changed.

`Joshua-reading.txt`, `Joshua-words.tsv` and `candidate-boundaries.md` are
generated by `python -m biblecore corpus`; don't hand-edit them. They carry
native Hebrew as reference data: don't copy it into chat or a fragment;
transliterate. `Joshua-english.txt` is provenance only, never the base of the translation.

Transliteration is core's (scheme: style reference §5; bible-core's
`tests/test_hebrew.py` is the authoritative definition).

## Session files

`session_index.md` (read first: standing state plus one line per recent session; older
lines go to `archive/`), `improvements_log.md` (only what git can't show: decisions, reverts,
gotchas), and `session_summary_<date>.md` (only for substantial sessions with open questions).
